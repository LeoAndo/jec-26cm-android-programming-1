いっぽう、次の3つはAndroidの仕組みとして決まっている動きです。端末による差はありません。

  • setPadding は余白を足すのではなく置き換える（Aの原因）
  • WindowInsetsCompat.Type.systemBars() にキーボードは含まれない（Bの原因）
  • 画面を回すとActivityが作り直される（Cの原因）

A. 画面の余白が消える

A-1. 何が起きているか

授業で作るアプリには、どの単元にも次のコードがあります。プロジェクトを新規作成したときにAndroid Studioが入れるコードです。

MainActivity.java · どの単元にもあるひな形
ViewCompat.setOnApplyWindowInsetsListener(findViewById(R.id.main), (v, insets) -> {
    Insets systemBars = insets.getInsets(WindowInsetsCompat.Type.systemBars());
    v.setPadding(systemBars.left, systemBars.top, systemBars.right, systemBars.bottom);
    return insets;
});

これは、画面の上の時計や電池が並ぶ帯（ステータスバー）と、下の帯（ナビゲーションバー）に部品が隠れないよう、@+id/main の部品に余白を入れる処理です。

大事なのは setPadding の動きです。足し算ではなく、置き換えです。もともと入っていた余白は、この行が動いた時点で消えます。

だから、ここに書いた余白は消えます

レイアウトの一番外側（@+id/main が付いた部品）に android:padding を書いても、実機では setPadding に上書きされます。縦向きの端末では左右のシステムバーが 0 なので、左右の余白は0になり、部品が画面の端にくっつきます。

見分け方

Android StudioのPreviewには余白が見えるのに、Runすると消える。これならこの現象です。Previewはレイアウトだけを描くので、setPadding が動かないためです。

A-2. 余白を入れたいとき

3つのやり方があります。授業のアプリでは方法1がいちばん簡単です。

方法1：部品のほうに layout_margin を書く（おすすめ）

一番外側ではなく、中の部品に余白を指定します。setPadding が書き換えるのは一番外側の部品だけなので、中の部品の指定は消えません。

activity_main.xml · 中のボタンに余白を付ける
<Button
    android:id="@+id/btn_start"
    android:layout_width="wrap_content"
    android:layout_height="wrap_content"
    android:layout_margin="12dp"
    android:text="スタート" />
書き方意味
android:layout_margin="12dp"上下左右に12dpの余白。
android:layout_marginHorizontal="12dp"左右だけに余白。
android:layout_marginTop="12dp"上だけに余白。

padding は「部品の内側」、margin は「部品の外側」の余白です。ボタンの文字とボタンの枠のすき間を広げたいときは padding、ボタンと画面の端のすき間を空けたいときは margin を使います。

方法2：一番外側の内側に、もう1つ入れ物を置く

部品が多くて1つずつ指定するのが大変なときは、@+id/main の内側にもう1つ LinearLayout を置き、そちらに padding を書きます。書き換えられるのは外側だけなので、内側の余白は残ります。

activity_main.xml · 入れ物を2重にする
<LinearLayout
    android:id="@+id/main"
    android:layout_width="match_parent"
    android:layout_height="match_parent"
    android:orientation="vertical">

    <LinearLayout
        android:layout_width="match_parent"
        android:layout_height="match_parent"
        android:orientation="vertical"
        android:padding="12dp">

        <!-- ここに部品を並べる -->

    </LinearLayout>
</LinearLayout>

入れ物が1つ増えるぶん、XMLは読みにくくなります。部品が少ないうちは方法1で足ります。

方法3：ひな形のコードを書き換える

ひな形の setPadding に、自分の余白を足して渡します。授業では使いません。ひな形のコードは単元を通して同じ形で説明しているためです。参考として、書き方だけ示します。

MainActivity.java · 参考
ViewCompat.setOnApplyWindowInsetsListener(findViewById(R.id.main), (v, insets) -> {
    Insets systemBars = insets.getInsets(WindowInsetsCompat.Type.systemBars());
    var extra = (int) (12 * getResources().getDisplayMetrics().density); // 12dpをピクセルに直す
    v.setPadding(systemBars.left + extra, systemBars.top + extra,
            systemBars.right + extra, systemBars.bottom + extra);
    return insets;
});

XMLの 12dp は、端末ごとの細かさに合わせてピクセルに直す必要があります。Javaでは自動で直らないため、この1行が増えます。

A-3. まとめ

やりたいことどこに書くか
部品と画面の端のすき間を空けたいその部品に android:layout_margin（方法1）
画面全体に同じ余白を入れたい内側にもう1つ入れ物を置き、そこに android:padding（方法2）
一番外側（@+id/main）に android:padding効きません。実機では消えます

授業で配られる完成プロジェクトでは、一番外側に android:padding を書いていません。効かない指定を残すと、Previewと実機で見た目が食い違い、原因を探すのが難しくなるためです。

B. キーボードが部品を隠す

B-1. 何が起きているか

入力欄（EditText）をタップすると、画面の下半分にキーボードが出ます。このとき、画面の下のほうに置いたボタンがキーボードの裏に入り、押せなくなることがあります。

原因は、A-1で見たひな形のコードです。

MainActivity.java · どの単元にもあるひな形
Insets systemBars = insets.getInsets(WindowInsetsCompat.Type.systemBars());

systemBars() は、ステータスバーとナビゲーションバーの2つだけを指します。キーボードは含まれません。そのためキーボードのぶんの余白が確保されず、部品がキーボードの下に潜り込みます。

見分け方

入力欄をタップする前はボタンが見えているのに、タップしたあとに見えなくなる。これならこの現象です。キーボードを閉じれば、また押せるようになります。

B-2. 直し方

ひな形の1行に、キーボード（ime）を足します。変更はこの1か所だけです。

MainActivity.java · キーボードも数に入れる
Insets systemBars = insets.getInsets(
        WindowInsetsCompat.Type.systemBars() | WindowInsetsCompat.Type.ime());

| は「どちらも」という意味の記号です。これで、ステータスバー・ナビゲーションバー・キーボードの3つを避ける余白が入ります。キーボードが出ると画面の中身が上に詰まり、ボタンが見えたままになります。

AndroidManifest.xmlの変更は要りません

android:windowSoftInputMode を書き足す方法も見かけますが、この1行だけで直ることを確認しています。

B-3. レイアウト側でできること

やり方効果
ボタンを入力欄より上に置くキーボードは画面の下から出るので、上にある部品は隠れにくい。コードの変更は不要。
全体を ScrollView に入れるキーボードが出ても、スクロールすれば下の部品に届く。
B-2の1行を足すいちばん確実。部品の並びを変えなくてよい。

授業で配られる完成プロジェクトでは、この対応を入れていません。単元ごとの学習内容に集中するためです。自分でアプリを作るときに、入力欄の下にボタンを置きたくなったら思い出してください。

C. 画面を回すとデータが消える

C-1. 何が起きているか

端末を横向きにすると、Activityがいったん壊されて、作り直されます。新しく onCreate が動くので、それまで変数に入れていた値や、ボタンの押せる・押せないといった状態は消えます。

授業のアプリで実際に確かめた結果です。

アプリ回す前回した後
A05BombGame1と2のボタンを押して、押せない状態にした9個とも押せる状態に戻る（ゲームの進行が消える）
A09MemoAppメモを1件追加したメモは残っている

なぜA09だけ残るのか

A09は onCreate で毎回 SharedPreferences からメモを読み直しています。Activityが作り直されても、ファイルに保存したデータは消えないので、読み直せば同じ内容が出ます。変数の中だけに持っていたA05は、読み直す先がないため消えます。

C-2. 残したいときのやり方

やり方いつまで残るか使いどころ
SharedPreferences に保存するアプリを終了しても、端末を再起動しても残る設定やメモなど、次に開いたときも欲しいもの。A08・A09で学んだ方法。
onSaveInstanceState に入れる回転などの作り直しの間だけ。アプリを終了すると消える入力途中の内容や、ゲームの途中経過。
ViewModel を使う同上（作り直しをまたいで残る）本格的なアプリ向け。Androidプログラミング2で扱います。

いちばん簡単なのは1つ目です。「作り直されても困らないように、大事なものは保存しておく」と考えると分かりやすくなります。

C-3. 授業での扱い

各単元では画面回転時のデータ保持と、横向きのレイアウトを扱いません。単元ごとの学習内容に集中するためです。授業中は端末を縦向きで使ってください。

横向きにすると、部品が画面からはみ出して見えなくなることがあります。これも上と同じ理由で、各単元では対応していません。
